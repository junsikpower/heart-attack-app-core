# 하트어택 (Heart Attack)

심장박동을 수치화하여, 대화로 상대의 심박수를 먼저 올리는 사람이 이기는 게임.
상대는 AI 캐릭터 또는 다른 유저.

이번 개발 사이클은 **카메라 기반 심박수(PPG) 측정 엔진**에 집중했습니다.
게임 기능(싱글·멀티 플레이)은 동작하는 MVP 수준이며, 이 저장소는 PPG 측정을 어떻게 안정화했는지를 중심으로 정리했습니다.

**개발 환경**

- 플랫폼: Flutter 3.11.4 (Android / iOS)
- 상태 관리: Riverpod (StateNotifier)
- 심박수 측정: `camera` + `flutter_ppg` + 자체 보정 레이어
- 싱글 플레이: Gemini 2.5 Flash + `flutter_tts` + `speech_to_text`
- 멀티 플레이: Firebase Realtime Database + Agora RTC
- 데이터 수집: Cloud Firestore

## 1. 제작 배경

사람들은 점점 개인화되며 현실에서의 상호작용에 부담을 느낍니다. 그러나 상호작용이 부족해 생기는 외로움은 여전히 존재하고, 이를 SNS 등 다른 서비스로 대체하려 합니다. 문제는 그 대체재들이 양극단에 있다는 점입니다.

- 익명성을 강조하는 서비스(랜덤채팅 등)는 불법적으로 오염되기 쉽습니다.
- 투명성을 강조하는 서비스는 불특정 다수에게 개인정보가 공개되어 상호작용의 부담을 없애기 어렵고, 익명 서비스보다 재미도 덜합니다.

하트어택은 다음 네 가지를 핵심 가치로 삼습니다.

1. 게임을 통해 현실에서의 상호작용에 대한 부담을 해소한다.
2. 상호작용을 통해 외로움을 해소하고 흥미를 유발한다.
3. 상호작용 자체를 공략 목표로 만들어 플레이 의지를 유발한다.
4. 심박수를 게임 요소로 포함해, 현실에서는 알 수 없는 타인의 감정 변화를 확인하게 한다.

네 번째 가치가 이 프로젝트의 정체성이자 가장 큰 기술적 위험 요소입니다. 심박수를 신뢰할 수 없으면 게임 자체가 성립하지 않기 때문에, 이번 사이클의 최우선 과제를 **심박수 측정의 신뢰도 확보**로 잡았습니다.

## 3. 완성도

**PPG 심박수 측정을 제외한 나머지 기능은 모두 MVP 수준입니다.** 이번 사이클의 목표가 심박수 측정의 신뢰도 확보였기 때문에, 나머지는 기능 검증 수준에서 멈춰 있습니다.

**PPG 심박수 측정** — 집중 개발 완료

- 전면 카메라 + 디스플레이 광원 방식으로 전환하고, 그 위에 자체 보정 레이어를 얹었습니다.
- 실사용 가능한 수준까지 안정화되었으며, 남은 과제는 조명 급변 대응과 정확도 검증입니다.

**싱글 플레이 (AI 대전)** — MVP

- Gemini 2.5 Flash + TTS/STT로 음성 대화 루프가 동작하며, AI는 기본 심박 75에서 프롬프트 규칙에 따라 수치가 오르내립니다.
- 기본 TTS/STT 패키지를 그대로 써 응답 품질과 속도가 낮고, 승패 판정과 게임 규칙이 없습니다.

**멀티 플레이 (1:1)** — MVP

- 6자리 방 코드를 생성해 상대가 참가하면 Firebase RTDB로 양측 BPM이, Agora로 음성이 실시간 동기화됩니다.
- 자동 매칭과 재접속 복구가 없어 코드 공유를 전제로 하며, 유저 테스트 전에 자동 매칭 구현이 필요합니다.

**게임 시스템 (규칙 · 재미)** — 미구현

- 심박수를 올리면 이긴다는 골격만 있고 체력 바, 승리 조건, 라운드, 점수 체계가 없습니다.
- 실제로 플레이해 본 결과 목표가 없어 플레이 욕구가 생기지 않았고, 이것이 이번 사이클의 주요 과제로 남았습니다.

**데이터 수집 파이프라인** — MVP

- 통화 중 백그라운드 STT로 발화 텍스트를 받아, 그 시점의 양측 BPM과 함께 Firestore에 저장합니다.
- 어떤 발화가 심박수를 올리는지 분석하기 위한 준비 단계이며, 아직 수집만 하고 분석 로직은 없습니다.

**UI / UX** — MVP

- 로비 → 사전 측정 → 매칭 → 게임으로 이어지는 다크 테마 화면 흐름과 실시간 파형 렌더링이 구현되어 있습니다.
- 텍스트 게임 화면(`text_game_screen.dart`)과 게임방 상태(`room_provider.dart`)는 아직 비어 있는 스텁입니다.

## 4. PPG 구현 과정

카메라 심박수 측정(PPG)의 원리는 단순합니다. 손가락에 빛을 비추면 심장이 뛸 때마다 모세혈관의 혈액량이 변하고, 투과되는 빛의 양이 미세하게 흔들립니다. 이 흔들림의 주기를 세면 심박수가 됩니다.

```text
  광원           손가락          카메라          신호 처리       BPM
  ──────────     ──────────────  ──────────────  ──────────────  ──────────
  화면/플래시로  혈액량 변화로   프레임별        피크 검출 →     60000
  빛을 비춤      투과광이 진동   밝기 기록       RR 간격 산출    ÷ RR(ms)
```

문제는 이 신호가 손 떨림, 압력 변화, 조명 변화에 매우 쉽게 오염된다는 점입니다. 아래는 이를 해결해 온 순서입니다.

### 1차 — 자체 알고리즘 구현

측정의 모든 과정을 직접 디버깅할 수 있도록, RGB 평균값을 뽑아 피크를 검출하는 코드를 직접 작성했습니다.

결과는 실패했습니다. 정확도가 실사용이 불가능한 수준이었고, 더 큰 문제는 **수치가 틀린 이유를 설명할 수 없다는 것**이었습니다. 값이 튈 때마다 예외 처리를 덧붙이는 방식이 반복되면서 로직만 복잡해지고 정확도는 개선되지 않았습니다.

### 2차 — 실측 로그 수집과 원인 분석

감으로 수정하는 것을 멈추고, 측정 파이프라인 전체를 CSV로 기록하는 기능을 앱에 넣었습니다. (`CameraService.startLogging()` / `stopAndGetCsv()`)

```text
Timestamp(ms), isGoodSignal, filteredIntensity, rrIntervals_count,
medianRrMs, rawBpm, filteredBpm
```

로그 기록을 **품질 불량으로 인한 측정 스킵보다 앞에 배치**한 것이 핵심입니다. 버려지는 데이터까지 남겨야 원인을 확인할 수 있기 때문입니다.

이렇게 7차에 걸쳐 수집한 실측 데이터가 [`predata/`](./predata) 폴더입니다. 여기서 네 가지 원인이 확인되었습니다.

1. **스파이크 노이즈** — 단일 프레임 만에 85 → 180 BPM으로 튐. 생리적으로 불가능한 변화.
2. **계단 등반형 드리프트** — 손가락 압력이 조금씩 변하면 100 → 105.8 → 112.5로 천천히 상승. 스파이크 필터로는 걸러지지 않음.
3. **기계적 격자 고착 (Grid Lock)** — 카메라 30 FPS(33.33ms) 샘플링 특성상, 노이즈 값이 112.5나 180.0 같은 특정 수치에 소수점까지 동일하게 고착됨.
4. **`isGoodSignal`의 한계** — 패키지의 신호 품질 판정은 광학적 안정성만 검사하므로, 기계적 노이즈를 정상 신호로 통과시킴.

여기서 추가로 확인된 사실이 있습니다. "소수점이 고정되면 노이즈"라는 규칙을 세우려 했으나, 자세가 매우 안정적일 때는 정상 데이터도 5초 이상 `85.714286`처럼 고정되었습니다. 즉 무변이를 에러의 유일한 기준으로 삼으면 정상 데이터까지 폐기하게 됩니다.

결론은 **소프트웨어로 모든 물리적 오차를 걸러낼 수는 없다**는 것이었습니다. 목표를 '완벽한 측정'에서 '사용 가능한 수준의 보정'으로 조정했습니다.

### 3차 — flutter_ppg 도입과 투 트랙 보정 로직

핵심 피크 검출은 검증된 `flutter_ppg` 패키지에 위임하고, 그 위에 자체 보정 레이어를 얹는 구조로 전환했습니다.

기존의 복잡한 예외 처리를 모두 폐기하고, 모든 상황을 두 가지 기준으로만 처리합니다. (기획안: [`implementation_plan.md`](./implementation_plan.md))

```text
              PPG 신호 수신
                    |
        ┌───────────┴────────────┐
        |                        |
        손을 뗐을 때             손을 대고 있을 때
        [ 트랙 1 ]               [ 트랙 2 ]
        120프레임(4초) 지속 시   이상값이 나와도
        완전 초기화 후           초기화하지 않고
        콜드 스타트로 복귀       직전 값을 계속 유지
```

**트랙 1 — 완전 초기화는 손을 뗐을 때만**
알고리즘 내부 사정에 의한 강제 리셋을 없애고, 초기화 결정권을 사용자의 물리적 행동에 넘겼습니다. 손을 뗀 상태가 120프레임(약 4초) 지속되면 0.0으로 초기화하고, 재개 시에는 이전 심박수와 무관하게 앱을 처음 켠 것과 동일한 조건에서 시작합니다.

**트랙 2 — 손을 대고 있는 한 직전 값을 유지**
비교 기준을 '직전 원시값'에서 '직전 필터값 대 현재 원시값'으로 바꿔 기준선을 안정화했습니다. 실제 심박수는 0.03초 만에 20 BPM씩 변하지 않으므로 부드럽게 추적되고, 명백한 오류(70 → 200)는 계속 차단됩니다. 수치가 오래 멈춰 있으면 사용자가 손을 떼게 되고, 그러면 트랙 1이 발동합니다.

**적용된 보정 파라미터** (`lib/services/camera_service.dart`)

- **표본 수** — `rrIntervals`가 3개 미만이면 신뢰 불가로 보고 직전 값 유지
- **대푯값** — 산술 평균을 폐기하고 중앙값(Median) 사용, 이상치 영향 제거
- **생리적 컷오프** — 40 BPM 미만 또는 190 BPM 초과는 즉시 폐기
- **콜드 스타트** — 10프레임 연속 편차 8.0 이내이고 후보값이 40~100일 때만 시작점으로 인정
- **스파이크 방어** — 직전 필터값과 18.0 넘게 차이 나면 무시하고 직전 값 유지
- **평활화** — EMA 계수 0.98 : 0.02로 미세한 흔들림 제거
- **손 뗌 판정** — 패키지가 손을 떼도 `isGoodSignal = true`를 유지하는 문제가 있어, `rrIntervals`가 비는 시점을 기준으로 판정
- **완전 리셋** — 불량 신호 120프레임에서 단 한 번만 초기화(Edge-trigger)하여 대기 중 CPU 부하 제거

### 4차 — 후면 카메라 방식의 한계

보정 로직이 자리를 잡자, 측정 방식 자체의 문제가 드러났습니다. 후면 카메라에 손가락을 대고 플래시를 켜는 표준 방식은 광원이 강해 신호는 잘 잡히지만,

- 플래시가 손가락을 매우 빠르게 뜨겁게 만듭니다.
- 발열로 휴대폰 자체의 작동에도 문제가 생깁니다.

하트어택은 몇 초 측정하고 끝나는 앱이 아니라, 한 판 내내 손가락을 대고 있어야 하는 서비스입니다. 따라서 이는 튜닝으로 해결할 문제가 아니라 방식 자체가 맞지 않는 문제였습니다.

### 5차 — 전면 카메라 + 디스플레이 광원 전환

플래시를 광원으로 쓰는 것을 포기하고, **화면 자체를 광원으로 쓰는 방식**으로 전환했습니다. (현재 방식)

```text
   [ 4차 : 후면 카메라 ]              [ 5차 : 전면 카메라 ]

     ┌────────────────┐               ┌────────────────┐
     │                │               │ ██ LIGHT BAR ██│  ← 손가락을 얹는 위치
     │                │               │                │
     │                │               │   screen 100%  │
     │                │               │                │
     └────────────────┘               └────────────────┘
        뒷면 : 렌즈 + 플래시              앞면 : 전면 렌즈 + 화면 광원

     광원 : 물리 플래시                  광원 : OLED 디스플레이
     발열 : 심함, 장시간 측정 불가        발열 : 없음, 장시간 측정 가능
     조명 : 외부 조명 영향 없음           조명 : 외부 조명 변화에 취약
```

**구현 내용**

1. 화면 밝기를 최대로 올리고, 전면 카메라(노치·펀치홀) 주변을 순백색 광원 바로 덮습니다. → [`PpgLightBar`](./lib/ui/widgets/ppg_light_bar.dart)
2. `main.dart`에서 Edge-to-Edge 모드를 적용해, 안드로이드가 상태바 뒤에 덧칠하는 반투명 배경을 제거했습니다. 이것이 없으면 렌즈 바로 옆이 어두워져 광량이 부족합니다.
3. 그 위에 손가락을 얹어 측정합니다.

**카메라 설정 변경**

- 전면 렌즈 선택, `ResolutionPreset.low`로 프레임 처리 부하 최소화
- `ExposureMode.auto` — 손가락으로 렌즈가 덮이면 카메라가 어둡다고 판단해 감도를 증폭시키는데, 이때 증폭되는 빛은 피부를 투과한 붉은빛뿐이므로 맥박 신호가 더 선명해집니다.
- `FocusMode.locked` — 밀착 상태에서 초점이 계속 움직이며 생기는 노이즈 차단
- 물리 플래시가 없으므로 `FlashMode` 제어 코드 전량 제거

**결과**

- 조명 환경이 고정된 상태에서는 후면 카메라 방식보다 측정 정확도가 높습니다.
- 장시간 손을 대고 있어도 발열이나 기기 이상이 없어, 대화 게임에 적합합니다.
- 플래시가 없어 주변 조명이 급격히 변할 때 대응이 어렵습니다. 이 부분은 측정 로직 수정으로 해결할 예정입니다.

## 5. 앞으로 해야 할 것

**전면 카메라 방식의 실측 검증**
전환은 마쳤으나 전면 카메라 방식으로 수집한 실측 데이터가 아직 없습니다. 후면 방식과 동일하게 로그를 수집해, 특히 조명이 급변하는 상황에서의 신호 열화 패턴을 확보하고 보정 로직을 재조정해야 합니다.

**스마트워치 등 기준 장비와의 정확도 대조**
지금까지의 개선은 수치가 튀지 않는가(안정성) 기준이었고, 맞는 숫자인가(정확도)는 검증하지 않았습니다. 스마트워치·산소포화도 측정기와 동시 측정하여 다음을 정량화해야 합니다.

- 안정 시 / 대화 중 / 운동 직후 구간별 오차
- 실제 변화를 따라잡는 데 걸리는 지연 시간 (EMA 0.98 계수의 대가)
- 기기·피부톤·조명 환경에 따른 편차

**측정이 끝내 불안정할 경우의 대안**
환경에 따라 새로운 문제가 계속 발생하므로, 모든 오차를 보정하는 것이 가능한지에 대한 검토가 필요합니다. 전면 카메라 방식으로 마지막까지 안정화를 시도한 뒤에도 해결되지 않으면 다음을 검토합니다.

- 가짜 심박수, 또는 실제 측정값의 변화량만 사용하는 방식으로 게임 로직 전환
- 최신 스마트워치 대부분이 심박수 브로드캐스트를 지원하므로, 워치 연동으로만 서비스를 한정

**게임 규칙 수립**
싱글·멀티를 구현했으나 목표가 없어 플레이 욕구가 충족되지 않았습니다. 유저 실험 전까지 체력 바 등의 게임 요소와 승리 조건·라운드 규칙을 설계해야 합니다.

**피실험자 모집 및 실험 계획 수립**
심박수 문제가 해결되는 즉시 유저 테스트를 진행할 예정이나, 아직 모집 계획이 없어 실험 설계와 함께 수립이 필요합니다.

flutter pub get
flutter run
